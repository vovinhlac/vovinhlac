## How I work

I keep portfolio engineering work reviewable through the same workflow I would use on a team:

`Issue / acceptance criteria` → `focused branch` → `atomic commits` → `pull request` → `CI checks` → `merge`

Branch names use clear intent such as `feat/`, `fix/`, `refactor/`, `perf/`, `security/`, `ci/`, `docs/`, and `chore/`. Commit subjects follow Conventional Commit-style prefixes so history stays easy to scan, review, and revert.

### Git practices demonstrated

- Issue-driven development with explicit scope and acceptance criteria
- Feature/fix/test/CI branches instead of committing directly to `main`
- Small, atomic commits with descriptive Conventional Commit-style subjects
- Pull requests with implementation, trade-off, security, and validation notes
- CI gates for PHP compatibility, syntax, coding standards, frontend builds, and repository hygiene
- Automated unit tests for core PHP behavior and security-sensitive primitives
- Reproducible public snapshots that intentionally exclude credentials and production-only data
